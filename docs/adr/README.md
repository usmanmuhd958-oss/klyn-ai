# KLYN AI OS - Architecture Decision Records\n\n## ADR-001: Unified Event-Sourced Kernel\n**Date:** 2026-07-03\n**Status:** ACCEPTED\n\n### Context\nThe system requires a reliable, auditable, and replayable execution model across distributed agents and regions.\n\n### Decision\nImplement a unified event-sourced kernel using:\n- **Append-only event log** (RocksDB)\n- **Raft consensus** for distributed coordination\n- **Deterministic replay** for audit and recovery\n- **Snapshot manager** for performance optimization\n\n### Rationale\n- Event sourcing provides complete audit trail\n- Raft ensures consistency across regions\n- Replay enables perfect recovery from any point in time\n- Separates concerns: storage, consensus, replay logic\n\n### Consequences\n- ✅ Complete auditability\n- ✅ Multi-region recovery\n- ✅ Deterministic debugging\n- ⚠️ Increased storage (but compactable via snapshots)\n- ⚠️ Requires careful consensus management\n\n### Implementation\n`services/kernel/src/event_store/` (Rust)\nEvent log with RocksDB backend, Raft consensus layer, replay engine\n\n---\n\n## ADR-002: Language Consolidation to Three-Tier Stack\n**Date:** 2026-07-03\n**Status:** PROPOSED\n\n### Context\nCurrent stack has 4 languages (Shell, Rust, Python, TypeScript) causing:\n- High cognitive overhead\n- Duplicate abstractions\n- Maintenance burden\n- Deployment complexity\n\n### Decision\nTarget three-tier language composition:\n1. **Rust (40%):** Kernel, runtime, core services (performance + type safety)\n2. **Go (35%):** Control plane, API gateway, orchestration (simplicity + concurrency)\n3. **TypeScript (25%):** CLI, SDK, web interface (developer experience)\n\n### Rationale\n- Rust for critical path (kernel, event store, cryptography)\n- Go for orchestration (excellent stdlib, concurrency primitives)\n- TypeScript for user-facing (familiar to JS ecosystem)\n- Eliminates Python and Shell as source code (use only for tooling)\n\n### Consequences\n- ✅ Reduced cognitive overhead\n- ✅ Better performance (Rust) and maintainability (Go, TS)\n- ✅ Clearer boundaries between tiers\n- ⚠️ Requires Go control-plane implementation\n- ⚠️ Shell scripts → Go migration effort\n\n### Implementation\n- Start: `services/control-plane/` (Go)\n- Migrate: `core/*.sh` logic to Go\n- Eliminate: `kernel/*.py` (move to `kernel/v6/` Rust)\n\n---\n\n## ADR-003: Capability-Based Security Model\n**Date:** 2026-07-03\n**Status:** ACCEPTED\n\n### Context\nAgents and services require fine-grained, revocable permissions.\nTraditional RBAC insufficient for multi-agent orchestration.\n\n### Decision\nImplement capability-based security:\n- Capabilities = unforgeable tokens granting specific operations on resources\n- Operations: read, write, execute, delete, delegate\n- Revocable and expirable\n- Constraints for additional restrictions (IP, time window, etc.)\n\n### Rationale\n- Least privilege: agents only hold minimal required capabilities\n- Revocation: instantly restrict agents without system restart\n- Delegation: agents can grant sub-capabilities to child agents\n- Auditability: all capability checks logged to event store\n\n### Consequences\n- ✅ Strong security boundaries between agents\n- ✅ Revocation without system restart\n- ✅ Minimal attack surface\n- ⚠️ Requires careful capability design per resource\n- ⚠️ Performance cost for capability verification (mitigate via caching)\n\n### Implementation\n`services/kernel/src/capability/` (Rust)\nCapabilityManager with grant/verify/revoke operations\n\n---\n\n## ADR-004: Deterministic Replay for Debugging & Recovery\n**Date:** 2026-07-03\n**Status:** ACCEPTED\n\n### Context\nAgents must produce reproducible results.\nOperators need ability to replay execution to any point for:\n- Bug investigation\n- State recovery\n- Audit trails\n\n### Decision\nImplement deterministic replay engine:\n- All inputs/outputs deterministic (no random without seeding)\n- Event log is source of truth for replay\n- Replay to any sequence number or timestamp\n- Verification: hash-based state checksums\n\n### Rationale\n- Perfect debugging: reproduce exact execution path\n- Recovery: restore state without reprocessing\n- Validation: detect divergence via state hash mismatches\n- Compliance: complete audit trail of all operations\n\n### Consequences\n- ✅ Perfect reproducibility\n- ✅ Time-travel debugging\n- ✅ Zero-downtime recovery\n- ⚠️ All RNG must be seeded from event log\n- ⚠️ External I/O must be idempotent\n\n### Implementation\n`services/kernel/src/replay/` (Rust)\nReplayEngine with replay_to() and verify_state() methods\n\n---\n\n## ADR-005: Monorepo Structure with Service Boundaries\n**Date:** 2026-07-03\n**Status:** PROPOSED\n\n### Context\nMultiple services (kernel, control-plane, API gateway, recovery) need:\n- Clear ownership and boundaries\n- Independent deployment\n- Shared infrastructure (proto, libs)\n- Coordinated testing\n\n### Decision\nMonorepo structure:\n```\nklyn-ai/\n├── services/\n│   ├── kernel/                 # Rust event-sourced kernel\n│   ├── control-plane/          # Go orchestration & routing\n│   ├── api-gateway/            # Go gRPC/REST gateway\n│   └── recovery/               # Go disaster recovery\n├── lib/\n│   ├── proto/                  # Shared protobuf definitions\n│   ├── go/                     # Go shared libraries\n│   ├── rust/                   # Rust shared libraries\n│   └── ts/                     # TypeScript shared libraries\n├── sdk/\n│   └── typescript/             # TypeScript SDK\n├── cli/\n│   └── typescript/             # TypeScript CLI\n├── tests/\n│   ├── integration/            # End-to-end tests\n│   ├── chaos/                  # Failure injection\n│   └── determinism/            # Replay verification\n└── docs/\n    ├── adr/                    # Architecture decisions\n    └── api/                    # API contracts\n```\n\n### Rationale\n- Clear service boundaries prevent entanglement\n- Monorepo enables atomic commits across services\n- Shared proto definitions ensure type safety\n- Independent deployment via service tags\n\n### Consequences\n- ✅ Clear ownership per service\n- ✅ Atomic multi-service commits\n- ✅ Reduced friction for cross-service changes\n- ⚠️ Requires careful CI/CD for independent deployment\n- ⚠️ Larger repo, but manageable with good tooling\n\n### Implementation\nCreate service structure above, migrate code incrementally\n\n
